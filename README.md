# 霁格相亭 · 相纸干燥配方

给自助相亭的待试纸制定干燥计时与返测顺序

模拟团队为 霁格相亭运维组有 9 人，负责 18 台自助证件照与旅行留影相亭。当前试机批次使用同一款 JG-M52 哑光相纸。。相亭记录纸面温度、环境湿度与出风风速。试机员从打印稿估计墨覆盖率，按固定间隔触纸检查，将首次通过耐擦检验的时刻抄入班次表。

- 高湿遇到大面积着墨时，原来的固定计时会把未干照片推入叠纸槽。
- 逐项加秒的经验表看不出湿度与墨覆盖率、湿度与出风的共同作用。
- 换环境后靠肉眼挑首测项目，异常条件和会拖慢相亭节拍的配方容易混在一起。

相亭环境读数、打印设备墨覆盖率和同一批相纸的历史耐擦记录 相亭值班员按优先级复测，负责人按工况审查试机配方单

## 业务模块

| 模块 | 工作内容 | 核心实体 |
|---|---|---|
| 相纸试样册 | CSV 校验、预览实测字段、以完整数据内容的 SHA-256 去重、追溯版本和下载原始数据 | 数据版本 |
| 干燥配方试算 | 按版本与领域参数创建计算单，由独立进程计算；从排队、成功或失败状态追溯 | 计算单 |
| 试机计时单 | 按业务字段查看度量、比较与排序，下载计算结果 | 计算单及其结果 |
| 班次交接 | 对结果样本作签发或暂缓，记录理由，导出选中样本并查看审计时间线 | 交接记录 |

## 算法及口径

**交叉特征子集选择与岭回归**。使用同一纸型的历史四项测量和首次通过耐擦检验的实际秒数。按日期排序后将前 60% 日期用于训练、随后 20% 用于选型、最后 20% 用于校准。保留四项主效应，对 (湿度−50)×(墨覆盖率−50)/100 与 (湿度−50)×(风速−1.2) 遍历无交叉、单项及双项共四种组合。各组只用训练组拟合标准化参数及固定 α=2 的岭回归。选型组 MAE 精确到 6 位小数，以更低误差优先，并列时优先保留更少交叉项，相同项数时优先保留湿度与墨覆盖率交叉。入选模型单独在最近的历史校准组计算实测减预测的单侧残差顺序统计量，排序位次取 ceil((n+1)×覆盖率)，负值截为 0。建议计时是预测与余量之和向上取整。最近校准数量不足、训练/校准日期不足、历史缺实测或待试机日期不晚于历史时提示修正。超出训练边界或超过 35 秒的试纸进入复核队列。

录入参数 **目标校准覆盖率（%）**，默认 90，允许范围 50–95。覆盖率越高，越倾向于留更长干燥余量，排序位次需要足量校准试纸。

### 留验比较与模型换用

「换用评估」页和 `/api/validations`、`/api/model-adoptions` 提供同一套服务端规则。导入的 CSV 可把带实测干燥秒数的样本标为 **留验试纸**；这些行按用途隔离，其日期不会进入新旧模型的训练、选型和校准，也可通过 `holdout_dates` 显式排除指定日期。

- 同一张留验试纸分别生成旧模型（默认取创建比较时的在用模型）和候选模型计时；建议计时小于首次通过耐擦检验的实测秒数时记为未干。
- 工况在查看留验结果前固定为「高湿重墨 / 高湿非重墨 / 非高湿重墨 / 非高湿非重墨」，阈值均为湿度 70%、墨覆盖率 70%。
- 不确定性按试机日成组，使用配对日差值计算单侧 95% t 置信上限，并附按日期重采样的确定性 bootstrap 区间。
- 只有整体平均计时缩短，且每个预设工况都有至少 2 个试机日、未干率差值（新−旧）的单侧置信上限不高于 0，比较单才标记为可换用。证据不足或任一工况上升时保留旧版。
- 比较单绑定创建时的在用模型键、规格指纹和换用状态；在用模型变化后，旧比较单返回 409，必须重新比较。
- 提交计算单时快照当时的模型键、指纹和覆盖率；之后换用模型不会改写仍在排队或重试的计算单。换用接口按比较单和 `Idempotency-Key` 幂等，重复请求只产生一次换用和审计事件。

演示数据额外提供 `JG-M52_20261126_留验比较包.csv` 的数据版本种子，其中含 6 个试机日、48 张分工况留验试纸；省时低余量候选 `swift-cross-v2` 会被安全门槛拦截。

演示集 `JG-M52_20261125_试机试纸.csv` 由 `backend/src/business/demo.py` 用固定数据或固定随机种子生成。工作台保留每次运行使用的输入版本、参数、结果和签审人。业务判断由服务端执行，前端图表直接读取返回的数值。

## 一天的工作剧本

1. 08:30 核对 18 个试机日期累计 144 张历史试纸，确认用的是 JG-M52 哑光相纸。
2. 08:45 收集从 JG-P01 到 JG-P08 的 8 张待试纸测量值，留空实际干燥秒数。
3. 09:00 打开 JG-M52_20261125_试机试纸.csv，查到 JG-P07 的湿度为 83%。
4. 09:10 以 90% 校准覆盖率发起试算，比较主效应、两种单交叉项和双交叉项的选型 MAE，确认保留的交叉项。
5. 09:15 对照其余参数相同的 JG-P01 与 JG-P02，核对较潮的 JG-P02 建议干燥得更久。
6. 09:20 优先安排 JG-P07 的边界返测，观察 JG-P06 是否超过 35 秒节拍。
7. 09:30 导出试机计时单，值班员据此进行新一轮耐擦试机。

docker compose up -d --build --wait

## 技术与配置

| 服务 | 技术与职责 |
|---|---|
| frontend | HTML/CSS/JS ES 模块，Nginx 静态页面与同源 API |
| backend | Python 3.11、FastAPI、SQLAlchemy、JWT |
| worker | Python 后台进程，使用 DB 的原子认领、租约与重试，输出 CSV |
| db | MySQL 8.0，存账号、版本、计算单和审计 |
| redis | Redis 7，通知 worker 尽快拾取，任务状态由数据库持久化 |

`FRONTEND_PORT`、`BACKEND_PORT`、`DB_PORT` 管理回环端口，`JWT_SECRET` 为签名密钥，`DB_PASSWORD` 为应用数据库口令，`DB_ROOT_PASSWORD` 为数据库 root 口令，`COMPOSE_PROJECT_NAME` 控制该栈的命名空间。

本地 Python 开发可用 `docker compose up -d db` 启动关系库，并另起一个仅绑定回环的 Redis。Compose 内的 Redis 通过容器网络连接。用 Python 3.11 安装 `backend/requirements.txt` 后，进入 backend 目录，设置 `DATABASE_URL`、`REDIS_URL`、`JWT_SECRET`、`ARTIFACTS_DIR`、`SEED_DEMO`，分别运行 `uvicorn src.main:app --reload`、`python -m src.worker`。ARTIFACTS_DIR 需已存在且由两进程共享。前端可使用 Compose Nginx 镜像并重建以加载修改，或用已有 Nginx 反向代理本地 Python 端口。

`backend/src/business/` 保存本题字段、生成器和算法，`backend/src/services/` 处理资源生命周期，`backend/migrations/` 是初始关系模式，`frontend/src/` 按页面、API、会话、组件、路由及样式组织。前后端枚举分别在 `backend/src/constants/workflow.py` 和 `frontend/src/constants/enums.js`。角色用于 JWT 路由与表单权限，计算状态用于队列与结果页，签审决定用于交接页、审计和签发导出。
